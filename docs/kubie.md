# Kubie в zsh

Kubie устанавливается отдельно на рабочих станциях с Kubernetes. Интерактивный zsh находит бинарник в Homebrew или `~/.local/bin` через общий `PATH`. В стартовой оболочке Kubernetes-индикатор скрыт. В каждой вкладке выберите контекст через `kubie ctx`: Kubie открывает отдельную сессию со своим временным kubeconfig. При наличии `KUBIE_ACTIVE` Starship показывает окружение и короткое имя кластера перед путём и Git в первой строке prompt. Namespace появляется рядом, когда он задан во временном kubeconfig сессии. `exit` возвращает в стартовую оболочку и скрывает индикатор; выбор в остальных вкладках сохраняется. Общие Bash/Zsh также передают контекст и namespace в [подпись вкладки Kitty](kitty-tabs.md), если нет назначенного вручную имени. [Руководство Kubie](https://github.com/kubie-org/kubie#usage), [модуль Kubernetes в Starship](https://starship.rs/config/#kubernetes).

## Структура kubeconfig и имена контекстов

Храните по одному кластеру в файле внутри `~/.kube/configs/`. Каталоги разделяют место размещения и владельца. Имя контекста имеет короткий формат `<env>:<cluster>`, например `dev:example` или `prod:core01`: Kubie использует его и в меню выбора, и в командах. Части пути `lab/` или `corp/<company>/` в имя контекста не входят.

| Категория | Путь относительно `~/.kube/configs/` | Имя контекста |
| --- | --- | --- |
| Домашняя лаба | `lab/<env>/<cluster>.yaml` | `<env>:<cluster>` |
| Локально на рабочей станции | `local/<env>/<cluster>.yaml` | `<env>:<cluster>` |
| Публичное облако | `public/<provider>/<account>/<env>/<cluster>.yaml` | `<env>:<cluster>` |
| Корпоративные | `corp/<company>/<env>/<cluster>.yaml` | `<env>:<cluster>` |

`<env>` принимает значения `dev`, `test`, `prod`. Имена контекстов должны быть уникальны среди всех файлов. При совпадении имён кластеров добавляйте к `<cluster>` короткое имя компании, аккаунта или региона, например `company-a-core01` или `eu1-app01`. Место размещения определяйте по реальному расположению: k3d или kind на удалённом сервере не относятся к `local`. Локальная копия production для экспериментов получает окружение `dev` или `test`.

Перенос файла не переименовывает контекст внутри него. Например, для нового тестового кластера с исходным именем `default`:

```sh
kubectl --kubeconfig="$HOME/.kube/configs/lab/test/example.yaml" \
  config rename-context default test:example
```

Эта команда меняет только локальное имя контекста. Ссылки на сертификаты и ключи в kubeconfig могут быть относительными: перед переносом сохраните их работоспособность. Если один кластер экспортирован в нескольких файлах с разными подключениями или учётными данными, сохраните версии раздельно и задайте разные имена контекстов.

Kubie сканирует `configs/` рекурсивно; служебный `~/.kube/kubie.yaml` и резервные копии вне этого дерева не попадают в список. Храните резервные копии, например, в `~/.kube/backups/<timestamp>/`, с доступом только владельцу: каталогам `0700`, kubeconfig `0600`.

`~/.kube/config` можно оставить как совместимую копию для обычного kubectl и программ, которые управляют этим файлом. Образец Kubie не сканирует его, чтобы копии контекстов не дублировались в меню. После изменения подключения или обновления credentials обновляйте используемые копии. Для файла, который перегенерирует сторонняя программа, повторяйте экспорт после её сброса или пересоздания кластера. Если контексты в `~/.kube/config` отсутствуют в `configs/`, его можно явно добавить в `configs.include`.

## Цвета prompt

| Префикс контекста | Вид | Пример |
| --- | --- | --- |
| `dev:` | Зелёный значок, метка `DEV` | `[☸ DEV example::app]` |
| `test:` | Жёлтый значок, метка `TEST` | `[☸ TEST example::app]` |
| `prod:` | Красный значок, без текстовой метки окружения | `[☸ core01::payments]` |
| Остальные | Фиолетовый значок, метка `? ENV` | `[☸ ? ENV default]` |

Все окружения имеют общий значок `☸`, который обозначает Kubernetes-блок. Окрашивается только значок; скобки, кластер и namespace сохраняют обычный цвет. Кластер и namespace разделяются двойным двоеточием: `cluster::namespace`; если namespace не задан, разделитель скрыт. Starship сопоставляет окружение по префиксу имени контекста. `dev:prod-simulator` остаётся DEV. В prompt `prod:core01` превращается в `[☸ core01::app]` с красным значком. Прежний формат `<env>/.../<cluster>` также поддерживается для уже открытых сессий. Индикатор отображается только внутри сессии Kubie с активным контекстом. Явные `--context`, `--kubeconfig` и `-n` у конкретной команды могут переопределить показанный выбор.

## Установка

На macOS с Homebrew выполните `brew install kubie`. Формула устанавливает completion, который общий zsh подхватывает через `compinit`. На Linux скачайте `kubie-linux-amd64` для `x86_64` или `kubie-linux-arm64` для `aarch64` из [релиза v0.28.0](https://github.com/kubie-org/kubie/releases/expanded_assets/v0.28.0), сравните вывод `sha256sum` с SHA-256 на странице релиза и установите проверенный файл как `~/.local/bin/kubie` с правами `0755`. Проверьте `kubie --version` в новой вкладке zsh. [Формула Homebrew](https://formulae.brew.sh/formula/kubie).

Из корня репозитория скопируйте образец, если локального файла ещё нет.

```sh
mkdir -p "$HOME/.kube"
(umask 077; cp -n examples/kubie.yaml.example "$HOME/.kube/kubie.yaml")
```

Если файл уже есть, перенесите в него `prompt.disable: true` и шаблоны `configs.include` из образца, сохранив остальные локальные настройки. Этот параметр передаёт отображение контекста Starship. Если файлы пока лежат в корне `~/.kube/`, сначала перенесите их в выбранные каталоги и переименуйте контексты. Храните kubeconfig и список приватных путей вне репозитория. [Настройки Kubie](https://github.com/kubie-org/kubie#settings).

При использовании собственного `STARSHIP_CONFIG` перенесите в него блок `[kubernetes]`, включая `detect_env_vars = ['KUBIE_ACTIVE']`, и все `[[kubernetes.contexts]]` из общего TOML и добавьте `$kubernetes` перед `$directory` в его `format`. При установке из отдельного бинарника можно подключить completion в `~/.zshrc.local.post` строкой `(( $+commands[kubie] )) && source <(kubie generate-completion zsh)`. [Локальные переопределения](local-overrides.md), [completion Kubie](https://github.com/kubie-org/kubie#autocompletion).

## Проверка в двух вкладках Kitty

1. Выполните `kubie lint`: контексты должны быть уникальными, а ссылки на clusters и users — корректными. Откройте две вкладки: в обеих Kubernetes-индикатор должен быть скрыт. Запомните вывод `kubectl config current-context` и состояние переменной `KUBECONFIG` командой `print -r -- "${KUBECONFIG-<unset>}"`. Команда `kubectl config current-context` читает локальный файл.
2. В каждой вкладке выполните `kubie ctx` и выберите разные контексты. Сверьте prompt и цветную метку `DEV`, `TEST`, `PROD` или `?ENV` во вкладке с `kubie info ctx`. Чтобы проверить namespace, задайте его через `kubie ctx ИМЯ_КОНТЕКСТА -n ИМЯ_NAMESPACE` или выберите через `kubie ns`. Эти команды по умолчанию обращаются к API выбранного кластера за списком namespace. Сверьте имя в prompt с `kubie info ns`.
3. В первой вкладке смените namespace через `kubie ns` и проверьте, что `kubie info ctx` и `kubie info ns` во второй не изменились.
4. Выполните `exit` в первой вкладке. Проверьте, что исходные контекст и `KUBECONFIG` вернулись, а Kubernetes-индикатор исчез. Во второй вкладке должен остаться её собственный контекст и namespace. Затем выйдите и во второй вкладке.
